# 项目定位与边界

## 一句话定位

内容证据核查 Agent 判断一段消费决策类内容里的关键说法是否站得住脚，并给出可回溯到原文与来源的核查报告。

## 背景

社区里大量高传播内容是消费决策类内容：测评、种草、对比、避坑。这类内容的问题不在于观点，而在于混入了无法核实的事实性说法，例如「续航 20 小时」「全系支持无线充电」「某机构认证」「90% 用户 4 周改善」。其中一部分是表述夸大，一部分是限定条件被省略，一部分是引用了过期资料。

运营人员现有的三种处理方式及其不足：

| 现有办法 | 不足 |
|---|---|
| 人工翻资料逐条核对 | 慢，不同人标准不一致，无法沉淀 |
| 用通用搜索或聊天工具问一句 | 得到一段结论，无法知道读了哪些资料、哪句话对应哪条证据 |
| 依赖审核规则与关键词 | 只能命中固定词，识别不了「数据真实但条件被省略」 |

核心缺口：缺少一条在保留证据链的前提下，把批量内容核查标准化、并把不确定的部分明确交回给人的流程。

## 目标用户

主用户是内容运营与社区治理人员，日常处理一定量的消费决策类内容，需要在有限时间内判断哪些内容需要干预、哪些只是观点表达。次要用户是内容创作者，在发布前自查表述是否存在条件省略或引用过期资料。演示语境下还有第三类使用者：验收方，用于判断项目有没有真实的产品判断，因此界面必须让「哪一步做了判断、为什么这样判断、失败时怎么办」在首屏可见。

## 用户任务

1. 从一段内容里确认哪些说法需要核查；
2. 看到每条说法的判断依据，并处理冲突或证据不足的条目；
3. 拿到一份可以交付、可以复核、可以追溯的报告。

## 与现有方案的差异

| 方案 | 覆盖的部分 | 缺口 |
|---|---|---|
| 通用聊天助手 | 快速给出结论 | 无证据定位，无失败可见性 |
| 长报告类检索产品 | 检索并生成带引用的长报告 | 报告级输出，无法按单条主张复核；引用常只到文档级 |
| 审核规则引擎 | 稳定、可规模化 | 只处理可枚举的风险，无法处理事实性核查 |
| 本项目 | 主张级判定 + 证据定位 + 人工复核队列 + 版本回归 | 不做内容发布、不做账号处置、不做大规模线上流量 |

差异点不在「用了 Agent」，而在于把判定粒度从整篇内容下沉到单条主张，并明确了哪些情况必须交回给人。

## 产品边界

不做：内容发布与账号处置、多租户与权限体系、通用 Agent 创建平台、模型训练与微调、实时爬虫、大规模并发调度。

## 人工介入点

只有两处：

1. **确认核查范围**：拆解出的主张有多有少，其中有些是营销修辞、有些与本次核查无关。此步让人删除无关主张，避免浪费检索与判定成本，也避免报告被无关条目淹没；
2. **处理冲突与不确定项**：资料互相矛盾、限定条件被省略、认证过期这类情况，机器可以识别但不能替人决定如何处置。系统把证据并排摆出来并给出建议，最终判断留给人。

除这两处不再插入确认。

## 成功定义

第一阶段只证明一件事：在人工标注的任务集上，系统能在证据不足时稳定地说「判断不了」，而不是硬给结论。这件事成立之后，第二阶段再看效率：人工复核一条主张需要多久、改判率有多高。

## 指标口径

任务质量：主张识别召回率、主张识别过度拆分率、主判定准确率、标志位召回率、无依据确定性结论率（核心指标）、引用有效率、复核队列命中率。定义见「评测指标」。

系统效率：单任务延迟、单任务成本、重试率与失败率。

用户行为（演示阶段埋点）：首次完整跑通任务所需时间、用户删改主张的比例、展开哪一步的 Trace、复核时采纳还是改判、在哪一步放弃、是否导出报告。

## 模型与评测纪律

默认模型 DeepSeek Flash（模型 id `deepseek-flash`，接口地址 `https://api.deepseek.com`）。接入时固定模型 id、温度与最大步数，并写入每次运行记录。

- 比较两个 Prompt 版本或工作流版本时模型必须固定，否则无法区分是 Prompt 的功劳还是模型的功劳；
- 换模型单独作为一条对比轴，报告必须标明所用模型 id；
- 每条任务的运行结果保留原始输出，人工评分基于原始输出；
- 温度默认为 0，需要采样多样性时单独记录。
