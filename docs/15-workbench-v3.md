# 15 工作台 v3：两个入口

对应 `10-prd-agent-v3.md` 第 7 节，是第 3 周的前半段。前两周产出的是脚本与数据，这一层把它们变成**能连续演示五分钟**的闭环。

## 为什么不是"再做一个 HTML demo"

界面是最后一层：先做界面，会得到一个漂亮外壳套在空的东西上——这正是项目早期"演示像版本更新日志"的成因。所以顺序是工具层 → 运行时 → 评测 → 界面。

另外，界面不是新建的：现有的 `app/server.py`（标准库 HTTP，无依赖）和三个视图继续用，本期只做增量。

## 三个入口，各自回答一个问题

| 入口 | 路径 | 给谁用 | 回答什么 |
|---|---|---|---|
| 处理内容 | `/agent` | 内容运营人员 | 这批内容里哪些说法需要我判断 |
| 评测与版本 | `/` | Agent 维护者 | 这个 Agent 跑得怎么样、版本之间差多少、差在哪几条主张上 |
| 工具与语料 | `/tools` | Agent 维护者 | 它能调用什么、边界在哪（只读规格页，不能在页面上改） |

平台入口顶部有一句说明，明确写给谁看——避免访客把它当成开发者调试台（PRD 7.1 的要求）。

## 处理内容：三列布局

页面分三列，宽度按"谁的注意力更值钱"排：

| 列 | 宽度 | 内容 | 为什么 |
|---|---|---|---|
| 左 | 290px | 待复核队列 | 只用来选，不需要宽 |
| 中 | 最宽（约 1.75fr） | 待复核的那条信息、证据、处置 | **这是人的工作对象**，字号放大到 18px |
| 右 | 次之（约 1fr） | Agent 检索过程 | 平时不需要看，按需展开 |

首屏不出现任何评测数字——运营不关心准确率，他关心这 5 条怎么处理。

队列按两条轴组织：

- 左边是**内容条级**的上下文：类别、原文、用户提供了哪些资料；
- 每一条记录落到**主张级**：具体是哪句话需要判断、为什么进队列。

这个两级结构直接来自定位修正（`11-scenario-validation.md`）：用户的工作单位是内容条，而证据链的单位是主张。

列表分两段：「需要判断」在上，「已可直接放行」在下。后者不是废数据——它证明 Agent 真的省掉了人工。

「已自动放行（可抽查、可改判）」这个措辞是修正过的：它是一份**可追溯的轨迹**，不是备份。三个处置按钮对两类条目都可用，随时能改判。

### 在原文里标出可疑片段

中列会把两处地方标出来，理由不同：

| 类型 | 样式 | 依据 |
|---|---|---|
| 数值与单位 | 与权威值不一致 → 红；一致 → 绿 | 可以被客观比对，唯一能自动判定的一类 |
| 断言词（唯一／全系／认证／治疗） | 琥珀 | 本身没错，但最容易省略限定条件，需要人看 |

鼠标悬停能看到具体依据，例如「与最权威来源相差 186%（21天，S-001）」。判定逻辑在 `src/evidence_agent/highlight.py`，服务端算好位置，前端只负责渲染。

高亮只影响提示，**不改变结论**——结论仍然由运行时的规则给。

### 材料写标题，不写编号

`S-006` 是数据库主键，给使用者看它是设计错误。现在每份材料显示为：

```text
口腔护理协会 2023 年度认证名录（旧版）
行业组织名录 · B 级 · 2023-09-10
```

格式是「标题 / 来源类型 · 等级 · 日期」。来源类型（品牌官方声明／独立检测／监管公开库／行业组织名录／平台规则／站内用户内容／站内营销内容）写在语料里，回答"这条材料是谁提供的"。

材料分两组：**依据的材料**（Agent 检索所得）与**手头已有的材料**（提交时给定的）。两组都有。

## 检索过程时间线

这是整个界面里最该被看到的部分：点开一条主张，能看到 Agent **每一步为什么选这个工具**。

```text
第 1 步  lookup_fact  baseline  OK  0ms
   为什么选它   certification 类型优先查事实库
   参数        entity=青禾 X1 · metric=认证
   结果        青禾 X1 认证：未列入 2025 年度名录（2025-06，口腔护理协会）（共 2 条）
   引用        S-005  S-006
```

三个设计细节：

1. **每一步都显示选择理由**，而不是只显示调用了什么。理由来自运行时的 `selection_reason`，是产品层的决策记录，不是日志。
2. **换策略会被标出来**：与上一步同工具标「换了参数重试」，不同工具标「换了工具」。GAP-006 那条会连着出现两个 `search_notes`，一眼能看出第一次查空了。
3. **降级单独提示**：`fetch_source` 定位失败时会显示「已降级」，不会假装拿到了准确定位。

右列默认只展开一行（工具 · 状态 · 为什么选它），参数、结果摘要与引用编号收在折叠里。

## 处置：三个出口，都不自动执行

每条主张下面三个按钮，对应 PRD 4.3 定的三个出口：

| 按钮 | 含义 |
|---|---|
| 放行 | 证据够，不处置 |
| 提示创作者修改 | 表述有问题，先提示 |
| 维持人工复核 | 需要更深处理 |

页面底部写着为什么只有这样三个：**系统只给建议，处置动作不自动执行——判错了被投诉的是平台。** 处置结果写进 `app/reviews.jsonl`，刷新后仍在。

## 版本对比（v3）

`/` 页的第三个标签。两次运行由使用者自己选（页面上两个下拉框），并且**只在同一类里比**：

| 选择 | 看到什么 |
|---|---|
| 两次评测运行（v1／v2） | 指标变化量 + 判定发生变化的案例清单 |
| 两次 Agent 运行（v3） | 指标 delta + **主张级变化**：状态／判定／标志位／处置档位 |

v3 没有标注可比，所以那边是@Q@两次运行互相比@Q@：同一条主张靠文本相似度配对，措辞变化不会被算成@Q@全变了@Q@。
跨类选择会被拒绝（界面提示 + 接口 400），因为两套指标口径不同。

对比逻辑在 `src/evidence_agent/agent_compare.py`，界面只负责渲染——和评测报告同一份口径。

## 工具与语料

每个工具一张卡片，把 Tool Registry 要求的六项全列出来：超时、重试、失败降级、单次成本、参数（含类型与必填）、返回。语料概况也放在页头——顺带说明语料里刻意包含过时与冲突数据，否则"自主检索"会退化成固定查找。

## 接口

本期新增三个只读接口，服务端把数据摊平成界面直接可用的形状，前端不做计算：

| 路径 | 说明 |
|---|---|
| `GET /api/agent-runs` | v3 Agent 运行列表（按 `results.json` 的结构与老评测区分） |
| `GET /api/queue?run=` | 待复核队列：内容上下文 + 主张级证据 + 检索步骤 + 已有处置 |
| `GET /api/tools` | 工具规格与语料概况 |

处置复用已有的 `POST /api/review`（`run` / `case_id` / `claim_index` / `decision`）。

服务端按结构区分两类运行：两类都是 JSON 对象，区别在顶层有没有 `metrics` 键——老格式是 `meta/summary/cases`，v3 是 `metrics/cases`。混在一个下拉框里比分数是最容易犯的错，而且 v3 运行出现在老列表里会显示成空视图（`cases=0`）。

## 已知局限

1. **没有登录与权限**：三个入口对所有人开放。上线才需要，作品集阶段不做。
2. **`reviews.jsonl` 是追加写**，没有并发控制与回滚；两个人同时处置同一条会各写一条记录，界面显示最后一条。
3. **导航是三个页面里各写一遍的静态标记**，没有构建流程可用，改动要同步三处。这是刻意选择的取舍：不引入前端构建链。
4. **界面只读加处置，不能在页面上发起新的评测运行**：跑评测仍然走命令行走 `harness/run_agent_eval.py`，跑完刷新即可看到。
5. 截图无法在自动化流程里落盘保存，因此本期的验收记录是逐页的可见文本核对，而不是图片比对。
