# 13 运行时（Agent 状态机）

对应 `10-prd-agent-v3.md` 第 5.1／5.2／5.4／5.5 节，是第 1 周的后半段。工具层解决"去哪查"，运行时解决"什么时候查够了、查不到怎么办、什么时候交回给人"。

## 状态机

```text
INIT → 对每条主张 [PLAN → ACT → OBSERVE → ASSESS]
         ├ 证据充分 → JUDGE（规则优先，规则判不了再叫模型）
         ├ 不充分且有策略 → 回到 PLAN
         └ 无策略／超预算／有阻断标志 → ESCALATE
     → AGGREGATE（分诊结果 + Trace）
```

三种终止状态必须分开记，因为它们对应三种不同的下游动作：

| 状态 | 含义 | 下游 |
|---|---|---|
| `JUDGED` | 有了结论 | 可放行，不必看 |
| `ESCALATED` | 已尽力，需要人判断 | 进复核队列，附证据包 |
| `TOOL_FAILED` | 工具连续失败，本次核查不可用 | 进队列，但原因不是"判断不了"，而是"系统不可用" |

把后两者混成一个"需复核"会掩盖系统可用性问题——**"查不到"和"查不了"是两回事**。

## 策略顺序

选择工具先用 `claim_type` 到工具的映射表定基线，失败后按固定顺序换策略。顺序写死，所以可复现、可评测、可解释：

```text
数值／认证／健康安全类：  查事实库 → 检索
其余类型：               检索 → 改写查询词 → 取原文定位段落
```

两条从实战里逼出来的约束：

1. **事实库查询需要"实体 + 指标"两个坐标。**只有实体没有指标时，查询会把该实体的全部记录拉回来，其中任意两项互相冲突就会误触人工队列——而那种冲突和当前主张无关。
2. **实体可以从正文里取。**主张句常常省略主体（"获得口腔护理协会认证"），主体在正文里。只在主张句里找实体，会让事实库查询白白空跑一次。

每一步都记录"为什么选这个工具"，写进 `selection_reason`，Trace 里可展开。

## 充分性判定

全部写成规则，模型没有否决权。三类情况直接转人工：

| 情况 | 标志位 | 判定依据 |
|---|---|---|
| 够格来源之间数值差超出该指标的容差 | `SOURCE_CONFLICT` | 同一实体同一指标、且**条件可比**，才谈得上冲突 |
| 条件或取样方式不同 | `NOT_COMPARABLE` | 厂商标称 vs 负载下实测——两个数不该直接比 |
| 新记录覆盖旧记录（相隔超过 365 天） | `STALE` | 跨年度的不一致不是冲突，是过期 |
| 只够格的来源不足 | `LOW_SOURCE_QUALITY` | 不算阻断，但证据不足 |

**低等级来源之间的分歧不算冲突。**夸大文案互相矛盾是噪音，不是矛盾。若把 C／D 也拉进冲突判定，任何一条带货文都能把结论拖进人工队列。

### 先判可比，再判差值

"两个数差得多就是冲突"这个做法是错的，两层修正：

**一、先问这两条记录说的是不是同一件事。**条件不同（一个标称、一个在 5V/2A 负载下实测）、取样方式不同（市场随机购买 vs 厂商送检），两个数根本不该放在一起比——那是**不可比**，不是矛盾。修正后，云石 P20 的 74Wh（厂商标称）与 62Wh（负载下实测）从"来源冲突"改判为"不可比"，理由也说得更准。

**二、容差按指标类型配，不再全域 10%。**测量类天生离散（续航 20%），标称类不该有偏差（容量、额定能量、功率、价格 5%）。原来那个 10% 是为了让语料里两条记录恰好判成冲突而倒推的，属于魔法数字，现在只是兜底值：

```python
TOLERANCE_BY_METRIC = {"续航": 0.20, "容量": 0.05, "额定能量": 0.05, "价格": 0.05, ...}
```

**三、会变的指标不算过期。**价格、销量、库存、排名这些在不同时间点数值不同是"变化"，既不是冲突也不是过期。这类指标出现分歧且主张没指明时间范围时，标 `NOT_COMPARABLE` 转人工。

### 来源分级：三个维度替代一个字母

原来的 A/B/C/D 把两件事压成一个值：来源**身份**和证据**强度**。"第三方检测"这个标签下混着有资质、市场随机购买的检测，和厂商送检的"特供样"（送检版与市售版不是同一批，这是行业公认问题），还有收了钱的商业评测。

拆成维度之后，**三个职责必须分开**（定稿口径见 `文档库/02-判定规则/来源分级.md`）：

| 层 | 回答 | 实现 | 谁在用 |
|---|---|---|---|
| 资格门槛 | 这条来源能不能单独支撑结论 | `_eligibility` | 充分性判定、`strong`、对外动作闸门（R13） |
| 权威排序 | 多条来源都够格时听谁的 | `rank_key`／`rank_key_for_row`（身份 → 取样 → 资质 → 日期，越小越权威） | `assessor.best()`、`compare_numeric()`、`highlight.authoritative_value()` |
| 展示权重 | 报告与界面显示什么强度 | 三档：0.90／0.70／0.40 | 报告、工作台、标记 |

**三个曾经踩过的坑，写在这里免得再犯**：

1. 资质与取样方式如果既进门槛又加进权重，就是同一个事实算两遍；报告里还会出现"0.85 + 0.10"这种看着像在算资格的算式。现在它们只决定门槛。
2. 排序不能用权重比大小：三档权重下"平台规则"与"厂商自述"曾经同分，谁更权威会退化成比日期。现在由元组第一位（身份）保证"监管 > 独立第三方 > 平台 > 厂商"。
3. 排序键四段必须**方向一致**（越小越权威）。日期字符串默认是"越大越新"，直接放进元组会让"取更新的那条"变成"取最旧的那条"——`score_sort_key` 把它折成"越新越小"，这条有回归测试锁定。

权重 ≥ 0.60 才算"够格的来源"。注意**厂商自述仍然是够格的**——核查"是否夸大宣传"时，厂商标称正是基准，把它当弱来源会让 GAP-005 这类主张直接判不了。

维度取值（`evidence_agent/grading.py`）：

| 维度 | 取值 |
|---|---|
| 来源身份 | 监管机构／独立第三方／平台机构／厂商自述／未知／用户自述 |
| 取样方式 | 市场随机购买／取样方式未说明／厂商送检 |
| 资质 | 有认可资质／无 |

"独立来源数"的口径：按**发布者**去重，不再按资料编号。同一家机构的两次检测、同一篇文章的两个转载版本，都只是一个来源。

## 判定：规则优先，模型补位

`compare_numeric` 处理能用数值直接比对的主张：抽出主张里的数值与单位，与最权威来源比对，偏差 10% 以内判定支持，否则判定冲突。

规则判不了的（例如"防水等级达到 IPX7"这类非数值表述）才叫模型，且模型只在**已检索到的证据包**上判断，不重新决定去哪查——这守住了 PRD 5.2 的"规则负责兜底，模型负责搜索"。没有配置模型时，这一类转人工并注明原因，而不是硬给结论。

## 预算

每条主张一个 `CallBudget`（4 次调用、30 秒）。预算耗尽即转人工，不算失败。

## 一次真实运行

`python harness/run_agent_demo.py`（不需要 API Key，走本地语料，可复现）：

```text
[已判定] 云石 P20 容量 20000mAh        SUPPORTED        lookup_fact
[转人工] 云石 P20 一次能给手机充 5 次    规则无法判定      search_notes
[转人工] 云石 P20 额定能量 74Wh        SOURCE_CONFLICT  lookup_fact
[已判定] 青禾 X1 标称续航 21 天         SUPPORTED        lookup_fact
[转人工] 获得口腔护理协会认证           STALE            lookup_fact
[转人工] 通过了欧盟 CE 认证            STALE            lookup_fact

分诊结果：2 条可直接放行，4 条需要人工
Trace：20 条事件
```

这组结果本身就是第 1 周的验收：一条内容端到端跑完，出现了数值支持、数值冲突、来源过期、规则无法判定四类不同结局，每一种都有独立的理由与证据编号。

## 已知局限（四个，都是真的）

1. **检索没有相关性阈值。**只要有一个字面命中就会返回，不相关的权威文档也能把"证据充分"顶起来——"一次能给手机充 5 次"这条就是被无关的民航规定文献撑成了"证据充分"。阈值需要评测数据才能定，所以留到评测阶段调，不在这里拍一个魔法数字。
2. **"认证"这类指标的粒度太粗。**事实库里"青禾 X1 的认证"指口腔护理协会认证，主张里的"欧盟 CE 认证"是另一件事，但两者会被当成同一指标比对，于是"通过了欧盟 CE 认证"被误判为过期。这是**误报**，不是漏报，需要按认证名称拆分指标才能解决。
3. **语义级冲突识别不了。**两条纯文本证据互相矛盾时无法识别，只有结构化字段（实体＋指标＋数值）才能触发冲突判定。
4. **"来源日期早于说法生效期"这条规则没有实现**，因为它需要解析主张自身的时间范围。

第 1、2 条正是评测阶段要处理的对象，也正是缺口任务存在的意义——它们的作用就是把这类错误找出来并给出界限。

## 测试

`tests/test_runtime.py` 共 30 个用例：充分性规则（冲突／过期／低等级／接近值不算冲突）、策略顺序、实体来源、预算隔离、三种终止状态、模型判定通路、Trace 事件。全套 91 个测试通过。
