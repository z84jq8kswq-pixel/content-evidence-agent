## 0. 这次验证要回答什么

五个必须能被证伪的问题：

| 编号 | 问题 | 什么结果算"不成立" |
|---|---|---|
| Q1 | 平台是否真的在处理事实性不实／误导内容 | 平台治理只覆盖色情暴力等违规，不碰事实问题 |
| Q2 | 现在靠什么手段做（人工／规则／模型） | 已完全自动化，人工不参与 |
| Q3 | 痛点在哪（量、速度、标准、可追溯性） | 效率与标准都不是问题 |
| Q4 | 是否已有产品解决 | 已有成熟产品覆盖同一场景与同一交付物 |
| Q5 | 核查的工作单位是整篇内容还是单条主张 | 单位是整篇内容，主张级拆分没有实际对应物 |

**怎么算这次验证失败**：如果五个问题全部指向"前提成立"，那说明我在找支持自己的材料，而不是在验证。按这个标准，本次验证是有效的——因为 Q3 与 Q5 都没有得到支持。

## 3. 逐问题结论

### Q1　平台是否在处理事实性不实内容——**成立（A）**

平台自曝半年处置虚假笔记 320 万篇，并明确点名虚假人设、虚假低质 AIGC、批量造假黑灰产。治理规模与"真实性"直接相关。

但有一个必须写清的限定：**披露的治理对象集中在"是不是真人真事、是不是批量造假、是不是低质"，属于真实性与营销性质问题**。"续航 20 小时是否属实""这个认证是否有效"这类**参数级事实主张**，在公开披露中没有单列。这既说明我选的场景没有被现有公告覆盖，也说明它可能不是一个被单独立项的治理目标。

### Q2　现在靠什么做——**成立（A），但形态与我原先设想不同**

手段组合：技术识别（同质化识别、机器对抗）+ 规则 + 用户举报 + 人工审核；被当作考核的效率指标是"虚假信息平均审核时长"（半年内同比 -25%）。

行业已经在用 AI 做单条查证：较真 AI 的链路是"结论-过程-评估"，含关键事实提取、多源证据比对、专业共识整合与可信度评分。

**形态差异（关键）**：平台的处置单位是**笔记与账号**；查证产品的核查单位是**一条说法**。二者不是同一层的东西。

### Q3　痛点在哪——**部分成立，但有一步没被证实**

可被证据支持的痛点：

| 痛点 | 证据 |
|---|---|
| 量极大 | 半年 320 万篇虚假笔记（A-1） |
| 速度被当作硬指标 | 审核时长同比降低 25% 被作为成果披露（A-1） |
| 人工模式被认为跟不上 | "旧有的人工查证模式已难以应对"（A-2） |
| 工具体验拖累效率 | 36氪报道（C-4） |
| 工作高压、高重复 | 新浪财经、澎湃、今日头条（C-2/C-1/C-5） |

**没有被证实的**：内容运营是否真的会为了判定一条内容，去逐条核查其中的事实性主张。

公开资料里，主张级核查出现在**专门的事实查证团队与产品**（较真），而不是社区运营的日常。运营侧的证据全部指向"条级、高速、按规则表判断"。

**这是本次验证最重要的修正。** 原 PRD 把"运营需要逐条核查主张"当作既定前提，这个前提目前不成立。

### Q4　竞品——**成立，且比我此前判断强得多**

我此前在项目文档里写"面向平台运营的、主张级核查加人工复核队列的成熟产品，我没有找到明确对标"。**这个判断需要更正。**

腾讯较真 AI（2025-08 上线）已经完成了我设想的核验链路产品化：结论-过程-评估、多源证据比对、可信度评分。它背后有 10 年查证积累、百万级辟谣数据库、专家库，以及"较传统人工查证效率提升 90%"的效率主张。

剩下的差异点只有四条，而且必须写清：

| 维度 | 较真 AI | 本项目 |
|---|---|---|
| 目标用户 | 普通用户（公众） | 平台内运营与治理人员 |
| 工作单位 | 单条说法，用户逐次提问 | 批量内容，逐条内容分诊 |
| 交付物 | 给用户看的查证结论 | 复核队列 + 可追溯证据链 + 处置建议 |
| 是否可被评测 | 是产品能力，不是被评测对象 | 自己就是评测对象，有任务集与版本对比 |
| 平台能力 | 不暴露 | Tool Registry、Trace、版本回归（Agent Infra 考察项） |

**诚实的判断**：在"查得准"这件事上，本项目不可能超过较真。本项目的价值只能是"面向站内的批量分诊 + 可评测迭代 + 平台化"。

### Q5　工作单位——**提问的答案是否定的（这是对 PRD 影响最大的一条）**

平台处置单位是**内容条**（笔记），查证产品单位是**主张（说法）**。两者并非同一层。

对本项目的直接后果：

1. "以主张为核查单位"作为内部实现是对的，但**主张只是中间产物**。
2. 运营的真实工作单位是"这条内容要不要处理"，因此**产品的入口、队列、统计口径都应该以内容条为单位**。
3. 如果演示只讲主张级判定，会和运营的实际工作单位脱节——这会再次产生"看起来像开发者工具"的问题。

## 4. 对 PRD 的修改建议

### 4.1 定位修正：从"查证"改为"分诊"

原定位：帮运营**逐条核查**内容里的事实性说法。

建议改为：

> 帮内容运营**判断一条内容里哪些说法需要进一步核实**，把可判定的直接给出带证据的结论，把判不了的连同证据一起交给人工——即以**内容条为单位做分诊**，以**主张为单位做证据链**。

理由：Q3 表明运营不做逐条核查，做的是条级快速判断；Q5 表明单位是内容条。把产品定位成"分诊"既贴合真实工作单位，也保留了主张级证据链这个技术优势。

### 4.2 需要改动的具体位置

| 文档位置 | 现状 | 建议改动 |
|---|---|---|
| `10-prd-agent-v3.md` 1.1／1.3 | 以"运营需要逐条核查主张"为出发点 | 改为"运营以内容条为单位处理大量内容，效率压力真实存在（审核时长被考核）；主张级核查是手段，不是用户任务" |
| 同文 3（用户与角色） | 主用户为内容运营 | 补充说明主用户的工作节奏是条级、高速，产品必须适配而非要求其逐条阅读 |
| 同文 新增 1.5 | 无竞品章节 | 新增竞品与差异化章节，写入 Q4 的五维对比表 |
| 同文 6.2（指标） | 只有主张级指标 | 增加内容条级指标：每条内容平均需人工处理的主张数、每百条内容的复核量 |
| 同文 11（风险 U1） | "痛点未验证" | 升级为"痛点已被部分证伪：不能以逐条核查为出发点"，并给出对应处置 |

## 5. 仍未验证的部分与下一步

### 5.1 本次没有解决的

| 未验证项 | 为什么重要 | 怎么补 |
|---|---|---|
| 运营的真实工作节奏与工具 | 决定产品是"分诊队列"还是"逐条核查台" | 需要 3 次从业者访谈 |
| 平台规则原文中是否包含参数级事实主张 | 决定这个场景在平台侧有没有立项依据 | 换渠道获取社区公约原文 |
| 虚假内容中"参数级不实"的占比 | 决定市场空间是否值得投入 | 自建小样本抽检，或查行业报告 |

### 5.2 三次访谈提纲

找人的优先级：在小红书／字节做过内容治理或社区运营的人 → 内容审核外包团队的一线人员 → 做过内容策略的产品经理。渠道：同学与校友、脉脉、公开的从业者社群。

访谈只问过去的行为，不问观点和假设：

1. 你最近一次处理"这条内容里的说法可能不实"是什么情况？当时是怎么判断的？
2. 一条内容你通常花多久？一天处理多少条？
3. 判断依据是什么——规则表、经验、还是去查资料？查资料一般查多久？
4. 什么情况下你会放弃判断、直接处置或上报？
5. 判错的代价是什么？有没有被要求复盘？
6. 现在用的工具哪里最烦？

**判定标准（事先定好，避免事后找解释）**：如果 3 人中有 2 人以上表示"日常不需要逐条核实说法、主要按规则表做条级判断"，则"分诊"定位成立，"逐条核查"定位废弃。
