## B. 界面改动清单（来自 2026-10-08 的反馈）

### B1　处理内容页改成三列

现在左列（队列）占了一整列且过宽，中列被挤。改为：

| 列 | 宽度 | 内容 |
|---|---|---|
| 左 | 窄（约 280–320px） | 待复核队列 |
| 中 | 最宽（约 1.6fr） | 这一条待复核的信息，**正文字号放大到 15–16px** |
| 右 | 次之（约 1fr） | Agent 检索过程（默认精简，按需展开） |

### B2　在原文里标出可能有问题的片段

中列展示待核查内容时，把可疑片段高亮：

- **数值 + 单位**（如"60 天""74Wh"）——与检索到的权威值不一致时标红，一致时标绿；
- **断言词**（如"唯一""全系""认证""治疗"）——标琥珀色，提示这类表述容易有条件省略。

需要后端在队列数据里补一个 `highlights` 字段，指出片段位置与原因，前端只负责渲染。

### B3　处置按钮配色

现在三个按钮长得一样。改为：放行 = 绿色、提示创作者修改 = 琥珀色、维持人工复核 = 蓝色。

### B4　待人工条目不再显示 `INSUFFICIENT`

待人工队列里判定恒为 `INSUFFICIENT`，恒定值不携带信息。改为只显示**进队列的原因**（过期／来源冲突／证据不足／检索用尽）与标志位。判定字段只在"已放行"段落显示——那里的值有变化，才有信息量。

### B5　证据与资料改用标题，不显示裸编号

`S-006` 这种编号对使用者没有意义。改为显示 `标题 · 日期 · 来源等级`，编号降级为副标题小字。来源：`data/corpus/sources.json` 的 `title` / `date` / `tier`。

### B6　页头文案澄清

现在写"用户给的资料不够"，读者会以为是发笔记的 C 端用户。改为明确的三件事：材料是**谁给的**、证据是**谁检索的**、语料是**离线的**（这一条必须写，否则会被误认为接了真实网络）。

### B7　"已可直接放行"改措辞

改成「已自动放行（可抽查、可改判）」，说明它是一份可追溯的轨迹，不是备份。

### B8　工具管理页的选项卡位置

根因已定位：`.topbar` 用了 `justify-content: space-between`，而 `tools.html` 少一个 `.topbar-controls`，三个元素变两个，选项卡被推到最右。

修法：`.topbar` 改 `justify-content: flex-start`，并给 `.topbar-controls` 加 `margin-left: auto`。这样三个页面结构一致，只靠一条规则控制右侧对齐。

## C. 待确认的一个问题

**这批"待核查内容旁边的材料"，在真实场景里应该算谁给的？**

这个答案决定页头文案、也决定数据结构（是"商家材料库"还是"运营上传"）。

我的判断与推荐：

- **权威材料（参数、认证、检测报告）的源头是 B 端**——商家／供应商在入驻与商品资质流程里提交，属于平台已有资产，不是运营临时找的；
- **被核查的内容本身来自 C 端**（发笔记和评论的用户）；
- **运营是材料的使用者，不是提供者**——让他们手工上传材料，等于把找资料的成本原样留给了人，产品价值会打折；
- Agent 另外还能检索**站内其他内容**与**公开权威来源**。

## E. 2026-10-08 问答产生的修正（优先级高于 B）

这一轮问答推翻了前面几处表述，动手前必须先改设计，否则会照着错的模型建。

### E1　来源分级从"一个字母"改成"多个维度"

> 状态：**已完成**（2026-10-11），实现为 `src/evidence_agent/grading.py`，见 `13-runtime.md`。

现在的 A/B/C/D 单字母分级太粗，把"来源身份"和"证据强度"混成了一个值。修正为至少三个维度：

| 维度 | 取值 |
|---|---|
| 来源身份 | 监管机构 / 独立第三方 / 厂商自述 / 平台站内 / 用户自述 |
| 取样方式 | 市场随机购买 / 厂商送检 / 不明（**送检样与市售品可能不是同一批，这是行业公认问题**） |
| 资质 | 有认可资质（CMA/CNAS 等） / 无 |

再补一个比 tier 更重要的判据：**独立来源数量**。结论应由"多个互相独立的来源一致"支撑，而不是"等级够高就发通行证"。

### E2　冲突判定先判"可比性"，再判差值

> 状态：**已完成**（2026-10-11）。云石 P20 的 74Wh 与 62Wh 已从"来源冲突"改判为"不可比"。

现在的规则是"A/B 之间数值差超过 10% 就算冲突"，其中的 10% 是**为了让语料里 74Wh 与 62Wh 被判成冲突而倒推出来的**，不是从数据来的。

修正为两步：

1. **先判可比吗**：测试条件是否一致（如"每天 2 次、每次 2 分钟"）、指标定义是否一致、时段是否重叠。不可比 → 标 `NOT_COMPARABLE`，**不是冲突**。
2. **可比再看差值**：容差按指标类型分别配置——测量类（续航、亮度）天然离散，容差应大；标称类（容量、额定能量、价格）容差应小；比例类指标另设规则。

另外，现在的"跨年度不一致 = 过期"对**会正常变化的指标**（价格、房价、销量）是错的——那是变化，不是资料过期。规则必须按指标类型分开定义。

### E3　材料来源清单（回答"还有哪些"）

按"是否依赖当事人自述"分三类，这是最重要的分类轴：

**A 类：客观可核查（不依赖当事人）**

- 市场监管总局：CCC 认证、能效标识备案
- 国家药监局：化妆品备案／注册、医疗器械、药品批准文号
- CNCA 全国认证认可信息公共服务平台：认证证书真伪与状态
- 国家知识产权局：专利、商标
- 全国标准信息公共服务平台：国标／行标／团标全文
- 卫健委：食品安全标准、保健食品
- 民航局等主管部门的运输与安全规定
- 有 CMA／CNAS 资质的检测报告、学术文献与专利文本
- 行业组织公开名录

**B 类：权威但属自述**

- 品牌官网与官方旗舰店的规格页（"厂商标称"）——用于核查**是否夸大宣传**时作为基准，不代表事实真相
- 品牌官方账号声明、主流媒体调查报道、披露方法学的专业评测

**C 类：平台内部数据（只有平台有）**

- 站内其他笔记与评论（同款商品的其他说法，可交叉验证）
- 品牌／商家账号的历史内容与商品链接
- **历史核查结论与人工处置记录（最被低估的一类：平台自己的判例库）**
- 用户举报记录、账号信用与历史违规

优先级：A 类 > C 类（站内交叉验证）> B 类。

### E4　修正 PRD 2.2 的非目标表述

原文写"不做真实网络爬虫"，容易被读成"产品不需要联网"。实际取舍是：

- **评测基线**不联网（保证同一任务集每次结论一致）；
- **真实产品必须联网检索**，而且"可复现"应该靠**结果快照**实现（把检索到的资料原文存档），而不是靠不联网。

这条同时解释了为什么证据留痕是核心功能：联网检索 + 快照 = 既实时又可追溯。

### E5　小红书场景没有强制商家入驻

之前用"商家入驻与资质流程"描述材料来源，那是淘宝／美团的模型。小红书以内容为主，大量笔记涉及的商品根本没在平台开店。所以真正的来源是：**品牌官方声明 + 监管公开库 + 站内内容**，不是"商家材料库"。

### E6　来源权威性机制要自建，不是采购

前一轮说"真实系统需要一套来源权威性机制"，容易被理解成存在现成服务可以直接买。据我所知**没有可采购的"来源权威性评级"服务**：搜索引擎的站点权威性排序是各家核心资产、不单独售卖；事实核查行业有共享的**结论库**（如 Google Fact Check Tools 聚合的 ClaimReview 标注），那是结论共享而非评级。

结论：这套机制应该自建，而且能自建——官方公开数据库可程序化查询且可验真（查证书编号），白名单是运营可维护的配置。通用来源评分反而解决不了领域问题。

> 状态：**已完成**（2026-10-11）。实现为 `src/evidence_agent/runtime/disposition.py`，
> 说明见 `17-disposition.md`；档位已接入评测与界面。

### F1　问题

现在的三个处置按钮（放行／提示创作者／维持人工复核）**混了三个不同层的问句**：

- 放行 = 改不改动
- 提示创作者 = 通知谁
- 维持人工复核 = 谁来处理

它们不是同一层的选项，所以放在一排会让人不知道该按哪个。更要紧的是，它默认了"这个工作台的作用就是提示创作者改"——**这个前提把产品做窄了**。

### F2　真实平台的手段（按风险从低到高）

| 档位 | 手段 | 风险 | 是否通知作者 | 使用频率 |
|---|---|---|---|---|
| 0 | **入库为判例**（沉淀样本，下次同类直接命中） | 无 | 否 | 每次都做，自动 |
| 1 | 放行（不改动） | 无 | 否 | 高 |
| 2 | **降级分发**（不进推荐池／搜索降权） | 低 | 否 | **最高** |
| 3 | 打标提示读者 | 中（需平台背书，判错要担责） | 否 | 中 |
| 4 | 通知创作者整改 | 中 | 是 | 中 |
| 5 | 转违规处置（下架等，须构成违规＋证据链） | 高 | 是 | 低 |
| 6 | 账号级处置（扣分／限流／封禁） | 最高 | 是 | 低 |

关键判断：**"提示创作者"排在第 4 档，不是全部，也通常不是首选。**首选一般是第 0＋2 档——不改动内容，只改变它获得的流量，同时把判断沉淀下来。在内容平台，"拿不到流量"比"删掉"更轻、更常见、争议更小。

这与 `10-prd-agent-v3.md` 4.3 节"事实判定是违规判定的证据之一，不是处置的触发条件"是同一条逻辑：被触发的是分发的放大或抑制，不是删除。

### F3　建议的界面改法

把一排按钮改成**按风险递增的档位选择**，并把"入库为判例"做成默认自动发生、不占按钮位：

```text
处置建议：降级分发（系统建议，可改）
[放行] [降级分发] [打标提示] [通知创作者整改] [转违规处置]
已自动入库为判例样本
```

这样按钮排布本身就说明了平台有哪些手段、风险怎么递增，而不是把三个不同层的动作并排放在一起。
