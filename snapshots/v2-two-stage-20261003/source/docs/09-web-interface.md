# 09 Web 工作台

## 怎么启动

```powershell
cd 'D:\JOB\实习\content-evidence-agent'
python app/server.py
```

打开 `http://127.0.0.1:8788`。不需要安装任何依赖，用的是标准库 HTTP 服务。

数据来自 `runs/` 目录，和评测报告同源。界面不会自己算一套数字，它复用 `evidence_agent` 里的 `aggregate`、`score_case`、`compare` 模块，所以界面上看到的判定准确率和 `report.md` 里的一定一致。

## 三个视图

## 顶部的运行选择器

每一行代表一次完整的评测运行：用某一套配置把任务集跑完一轮，结果落在 `runs/<运行编号>/`。切换它，三个视图全部跟着换——任务列表的判定、指标卡、Trace 的调用记录、对比的基准。

运行多了以后这个列表会误导人，因为不同运行的可比性完全不同。所以每次运行会记录**任务集指纹**（`eval_tasks.json` 的 SHA256 前八位），界面据此分四类：

| 类型 | 含义 | 能不能当质量结论 |
|---|---|---|
| 完整评测 | 30 条任务、真实模型、与当前任务集指纹一致 | 可以 |
| 旧任务集 | 跑在标注复查之前的任务集上 | 不能，当时的正确答案本身有错 |
| 子集测试 | 只跑了部分任务 | 不能，样本太小 |
| 离线桩 | 用离线桩适配器跑的通路验证 | 不能，桩被设计成故意答错 |

选择器默认勾选「只看可比较」，把 21 次运行收敛到 3 次真正的基线。取消勾选可以看到全部历史运行，此时选中不可比较的运行会显示一条黄色提示，说明它的指标为什么不能直接读。

这个字段是后补的。早期运行没有指纹，界面标注为「任务集版本未记录」，归入「旧任务集」。三次 `final-*` 运行是在标注复查之后跑的，核对过任务集修改时间后回填了指纹。

### 核查

回答"这条说法能不能发"。

左边是任务列表，标出每条任务的类别、模型判定和 P0 错误数。右边是选中任务的详情：待核查内容、可用资料、模型的逐条判定（含判定、标志位、引用编号、一句话依据）。

每条主张下面有四个处置按钮：采纳判定、改判为支持、改判为冲突、标记资料不足。处置结果写入 `app/reviews.jsonl`，刷新后仍在。

界面组织单位是**主张**而不是对话轮次。内容核查的基本单位是一条可独立验证的说法，所以没有聊天输入框，也没有消息流。

标注答案默认折叠。真实审核场景里审核员不应该看到标准答案，这里保留它是因为作品集演示需要让人看到"模型判对了没有"。

### 运行 Trace

回答"这次运行到底发生了什么"。

上半部分是当前任务每次调用的记录：步骤名、状态、耗时、输入输出 token、重试次数、结束原因。展开可以看到模型的原始返回。

下半部分是历史运行表，把所有运行按判定准确率、P0 数量和成本列在一起，方便横向看不同配置的差别。

这个视图不是给普通用户看的，是给调试看的。第一次接真实模型时空返回的问题，就是靠这份记录才发现真实原因是推理预算被烧光。

### 版本对比

回答"新版是不是真的更好"。

默认拿 v1 和 v2 两次运行做对照，逐项列出基准值、对照值、变化量和改善方向，下面是判定发生变化的案例清单，标出哪几条改对、哪几条改错。

只给一个总体百分比是不够的。案例清单能说明"多对的几条集中在什么类型上"，这比数字本身更有信息量。

## 接口

| 路径 | 说明 |
|---|---|
| `GET /api/runs` | 所有评测运行的摘要 |
| `GET /api/run?run=` | 单次运行的指标、成本和逐条结果 |
| `GET /api/case?run=&case=` | 单个案例的内容、资料、模型判定和调用记录 |
| `GET /api/compare?base=&compare=` | 两次运行的对比 |
| `GET /api/reviews?run=` | 已有的人工复核记录 |
| `POST /api/review` | 写入一条人工复核决定 |

## 目前没做的

界面是只读加人工处置，不能在这里发起新的评测运行。要跑新一轮评测仍然走 `harness/run_eval.py`，跑完刷新页面即可看到。

没有登录和权限体系，复核记录是追加写的 JSONL，没有并发控制和回滚。这些属于上线才需要的东西，作品集阶段不做。
