# 05 第一次真实模型运行记录

这份文档记录评测集第一次接真实模型时暴露的问题。它的价值在于证明这套指标不是摆设——它真的抓到了我自己没发现的问题。

## 运行环境

- 模型：`deepseek-flash`
- 接口：`https://api.deepseek.com/chat/completions`
- 管线：v2（先抽取主张，再逐条判定）
- 任务：30 条标注任务

## 问题一：推理预算失控导致空返回

**现象**：前两条任务的抽取调用全部失败，错误码 `EMPTY_RESPONSE`，耗时 6 秒以上，token 显示 0/0。

**排查过程**：第一次我以为是解析问题，改了解析器容错，但方向错了。后来把接口原始返回体存进 Trace，才看到真实原因：

```
finish_reason=length
reasoning_content 长度=11025
completion_tokens=3000 / max_tokens=3000
```

`deepseek-flash` 是推理型模型。抽取一条简单主张时，它生成了上万字的内部推理，把全部输出预算耗尽，最终 `content` 为空。

**修复**：加入推理强度参数。实测三种配置：

| 配置 | 耗时 | 输出 token | 结果 |
|---|---|---|---|
| 默认（无参数） | 14.7s | 3000（截断） | 空返回，失败 |
| `reasoning_effort=low` | 6.5s | 1231 | 成功，抽取干净 |
| `reasoning_effort=none` | 1.4s | 139 | 成功，但抽取质量下降 |

**结论**：`low` 作为默认值。`none` 虽然快 9 倍，但会把资料里的内容误当成待核查主张，抽取质量不可接受。

**产品含义**：推理型模型的"思考"是要花钱和花时间的资源，必须作为可配置项暴露出来。这也是 Agent Infra 平台上"按节点配置模型参数"这个功能的真实动机——抽取是机械任务，判定才需要推理，两者不该用同一个预算。

## 问题二：抽取时把资料当成主张

**现象**：在 `reasoning_effort=none` 下，模型从"官方规格：关闭降噪 40 小时、开启降噪 28 小时"里提取出两条主张，但这两条来自资料，不是待核查内容里的说法。

**修复**：提示词里加一条硬约束——只从待核查内容中提取主张，可用资料是判断证据而非主张来源。

## 问题三：评测集自身的标注矛盾

**现象**：EV-001 内容是"综合续航 40 小时是真的"，标注为 SUPPORTED。模型判为 PARTIAL + OMITTED_CONDITION，理由是官方规格里 40 小时是关闭降噪条件下的数据。

**排查**：对照标注规则文档，"主张省略了会改变结论的条件即判 PARTIAL"。而 EV-025 的表述方式与 EV-001 相同，却标了 PARTIAL。也就是说，错的是我的标注，模型的判断符合我自己写的规则。

**修复**：改 EV-001 的内容，明确写出"关闭降噪时"，使其成为真正的 SUPPORTED 案例；同时在标注规则里补一条——条件已经写在内容里的不算省略。

**为什么值得记录**：这是评测集第一次被真实模型"反向审查"。人工标注看上去自洽，实际存在不一致，只有跑起来才会暴露。这也是为什么先跑 3 条再跑全量，比直接跑 30 条更划算。

## 问题四：主张边界的灰色地带

模型把"每天通勤两小时""一周才充一次电"也抽取成了主张。这两条属于作者个人使用习惯，无法从外部资料验证。规则文档里补了排除条款，提示词同步更新。

## 指标口径的可信度检查

3 条小样本的结果：

| 指标 | 数值 |
|---|---|
| 主张召回率 | 1.0 |
| 主判定准确率 | 0.667 |
| P0 错误 | 0 |
| 输出格式违规 | 0 |
| 平均单任务耗时 | 19.5s |

唯一的主判定错误就是上面 EV-001 的标注矛盾。修掉之后，这个数字才有意义。

## 对全量运行的影响

按 3 条样本推算，30 条任务约需 9 倍调用量，也就是 90 次左右调用、8 到 10 分钟。如果推理强度用默认值而不降档，单次调用会因空返回而重试三次，时间和成本都会翻倍，这就是先做小样本验证的实际价值。
